# Правила работы с CargoFlow

## Перед реализацией

1. Прочитать `CargoFlow.md` и относящиеся к задаче файлы в `docs/`.
2. Изучить существующий код и сохранить несвязанные пользовательские изменения.
3. Простыми словами объяснить, что относится к Bitrix24, а что — к CargoFlow.
4. Перед изменением интеграции проверить актуальную официальную документацию Bitrix24 REST.
5. Ограничить изменение текущим этапом разработки.

## Инженерные правила

- Никогда не коммитить `.env`, адреса webhook, OAuth-токены, пароли и персональные данные.
- Для новых интеграций со сделками использовать `crm.item.*` и `entityTypeId = 2`.
- Проверять `auth.application_token` у исходящих событий Bitrix24.
- Каждая интеграционная операция должна передавать `correlationId`.
- Обработка webhook должна быть идемпотентной.
- Consumer подтверждает сообщение только после успешной обработки или надёжной повторной публикации.
- Публичные ошибки должны быть стабильными и не раскрывать внутренние детали или секреты.
- Бизнес-правила следует хранить в функциях и сервисах, удобных для тестирования.

## Definition of Done

Запустить применимые проверки:

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
docker compose config
```

Обновить документацию, дать инструкцию локальной проверки, предложить commit message и перечислить
нужные скриншоты. Не выполнять настоящий `git push` без явного разрешения пользователя.
